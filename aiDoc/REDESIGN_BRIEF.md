# 首页样式重构 · Claude Code 任务简报(Goal 模式)

> 给 Claude Code 的指令:这是一份**目标导向**的简报,不是逐步脚本。请先理解目标与硬约束,**自己探索现有代码、自己制定计划、分段实施、自己验收**。遇到与约束冲突或信息缺失的地方,停下来问,不要猜。

---

## 0. 一句话目标

把**现有的 GVA 首页**在视觉上完全按 `./design.png` / `./design.pdf` 重构,**保留全部现有功能,不丢任何一个交互**。这是一次「换皮不换骨」的重构:**行为先对齐,再追求视觉还原度**。

---

## 1. 硬约束(不可违反)

1. **功能零回退**:现有首页的所有路由跳转、i18n 文案、状态管理、事件处理、外链(GitHub/Gitee/GitCode、文档、立即体验)、视频播放、轮播、语言切换等,**重构后必须全部仍然工作**。如果某段视觉需要改 DOM 结构,先确认对应的逻辑/props/事件被迁移过去,而不是删掉。
2. **这是视觉层重构,不是重写**:优先复用现有组件与逻辑,只替换样式与布局。除非现有结构完全无法承载新设计,否则不另起炉灶。
3. **沿用项目现有技术栈与主题机制**:先查清楚现在用的是什么(Vue3?Tailwind / UnoCSS / SCSS?Element Plus?),把设计 token 落到**项目已有的主题体系**里,不要私自引入并行的样式方案。
4. **不擅自加重依赖**:需要新依赖(如轮播库)先列出来征求确认,优先用现有库或轻量实现。
5. **桌面 + 移动都要做**:设计画板里左列是桌面端、右列是移动端整页,两套断点都要还原(见 §5)。
6. **暗色模式/主题**:如果项目现在支持暗色或多主题,重构后不能破坏;新写的样式走 token,不写死颜色。
7. **文案走现有 i18n**:设计里全是中文,但**不要把中文硬编码**——如果项目有 i18n,新文案按现有 key 规范补进去(中英都补);拿不准时问。

---

## 2. 怎么读这两个设计文件

- `./design.pdf` 是更清晰的矢量源,`./design.png` 是同一画板的快照,**两者内容一致**。
- 画板是一整块,包含三部分:**左侧长列 = 桌面端整页**(从导航到页脚)、**右侧长列 = 移动端整页**、**中间漂浮的几张 = 局部放大截图**(hero 视频弹窗、流程生成面板等)。别被布局绕晕。
- 画板被缩得很小,**直接看读不清字**。建议把 PDF 按高 DPI 渲染成图、再分段裁剪放大来读(例如 `pdftoppm -r 300` 或 PyMuPDF `Matrix(5,5)`,然后按纵向条带 crop)。本文档 §4 已经替你把每个区块的文案和布局读出来了,**优先以 §4 为准**,设计图用来核对视觉细节(间距、圆角、阴影、配色)。

## 3. 设计 Token(从设计稿实测提取,落到项目主题体系)

| Token | 值 | 用途 |
|---|---|---|
| `--color-primary` | `#2465F2`(鲜艳宝蓝) | 主按钮、强调文字、链接、区块小圆点标签、激活态 |
| `--color-text-strong` | 近黑 `#0B0B0F`~`#111` | 大标题 |
| `--color-text-body` | 中灰 `#5A5F6B` | 正文段落 |
| `--color-text-muted` | 浅灰 `#8A8F99` | 图注、次要说明 |
| `--bg-base` | `#FFFFFF` / `#FDFDFD` | 普通区块底色 |
| `--bg-alt` | `#F7F7F7` | **交替**出现的浅灰区块底色 |
| `--bg-dark` | `#0A0E1A`(近黑藏青) | 终端代码块、页脚 |
| `--color-success` | 约 `#16A34A` | ✓、成功态终端绿色边框 |
| `--color-danger` | 约 `#EF4444` | ✗、失败态终端红色边框 |

**反复出现的视觉规律(请贯穿全站):**
- **区块标签**:每个区块标题上方有一个「`●` + 小号蓝色标签文字」(如 `● 工具兼容`、`● Skills 系统`)。
- **标题高亮**:每个大标题里有**一小段关键词用主蓝色**,其余近黑。例:用 **AI** 构建系统 / 从 **一句话需求** / 已有 API,**一键生成** / 安全、可靠、**可控**。务必保留这个高亮模式。
- 卡片圆角约 12–16px,1px 浅边框 + 柔和阴影。
- 全宽区块标题**居中**;「文字 + 配图」类功能区块用**两栏**(一边文案一边视觉)。
- 大号「幽灵数字」01–04 用极浅灰。
- 纵向留白充裕,区块之间节奏明显;**浅灰区块与白色区块交替**出现。

## 6. 建议的工作流(Goal 模式 · 你自己执行)

> 不要一上来就写代码。按阶段推进,**每阶段产出可检查的东西**。

- **阶段 0 · 探索 + 计划(先做,写成文件)**
  - 读现有首页代码:组件树、props/events、路由跳转、i18n key、状态管理、当前样式方案。
  - 把 PDF 渲成高清图分段读细节;以本简报 §4 为骨架。
  - 产出 `REDESIGN_PLAN.md`:① 设计区块 ↔ 现有代码 映射表(已有/改造/新增)② 每个区块要保留的功能点清单 ③ token 落地位置 ④ 实施顺序 ⑤ 风险与待确认问题。**先把待确认问题抛出来。**

- **阶段 1 · Token**:把 §3 的颜色/字号/间距/圆角/阴影落到项目主题体系,先建底座。

- **阶段 2 · 分段实施(自上而下,导航 → 页脚)**:每做完一个区块,确认它能渲染、且**原功能仍工作**,再做下一个。改 DOM 前先迁移逻辑。

- **阶段 3 · 响应式**:按 §5 过一遍移动端。

- **阶段 4 · 自检验收**:对照 §7 清单逐条核。

## 8. 什么时候停下来问(不要猜)

- 现有首页技术栈或样式方案不明确时。
- 设计里的某区块在现有代码里**找不到对应功能**(是纯新增静态区块,还是需要接真实数据/接口?)。
- 文案该走 i18n 还是允许先占位。
- 任何会**改变现有交互行为**的取舍。
- 需要新依赖时。
